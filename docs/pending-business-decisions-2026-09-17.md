# 업무 결정 대기 항목 (2026-09-17, 1차 작업 후)

코드로 정답을 정할 수 없어 **업무·세무 담당자 결정이 필요한 항목**만 모았다.
각 항목의 현재 코드 동작과 선택지별 영향을 적었고, 이번 작업에서 임의로 고르지 않았다.
예시 금액은 모두 가상 값이다.

---

## D1. 셀러(인플루언서) 정산 공식

### 현재 공식 3개 — 같은 입력에서 결과가 다르다

| 위치 | 용도 | 프리랜서 | 간이사업자 | 사업자 |
|---|---|---|---|---|
| `app/routers/settlements.py` `calc_settlement` | **실제 정산 저장** (수동 등록·재계산·캠페인 완료 자동 생성) | 커미션 − (커미션 ÷ 1.1) × 3.3% | 커미션 − 커미션 × 10% | 커미션 |
| `app/sourcing/pricing.py` `settle` | 소싱 검수 화면 정산표 (표시) | 커미션 − 커미션×10% − (커미션×90%)×3.3% | 커미션 − 커미션 × 10% | 커미션 |
| `app/templates/campaigns/form.html` 미리보기 | 캠페인 폼 정산 미리보기 (표시, "참고용" 문구 추가함) | 커미션 ÷ 1.1 − (커미션 ÷ 1.1) × 3.3% | 커미션 (차감 없음) | 커미션 |

가상 예시 — 판매금액 10,000,000원, 수수료 10% → 커미션 1,000,000원

| 셀러 유형 | 실제 저장 | 소싱 검수표 | 캠페인 폼 미리보기 |
|---|---|---|---|
| 프리랜서 | 970,000 | 870,300 | 879,091 |
| 간이사업자 | 900,000 | 900,000 | 1,000,000 |
| 사업자 | 1,000,000 | 1,000,000 | 1,000,000 |

### 결정해야 할 항목

1. **커미션 기준 금액.** 수수료율을 곱하는 금액은 무엇인가?
   - 현재: 캠페인 `actual_revenue`(판매 총액, 소비자 결제액)
   - 선택지: 결제 총액 / 배송비 제외 / 부가세 제외 공급가액 / 취소·환불 차감 후 순매출
2. **커미션에 부가세가 포함돼 있는가.** 계약서의 "수수료 N%"가 부가세 포함 금액인지 별도인지.
3. **간이사업자 차감.** 커미션에서 10%를 빼는가(현재 저장 공식), 빼지 않는가(현재 폼 미리보기).
4. **프리랜서 원천징수(3.3%)의 과세표준.**
   - A: 커미션 ÷ 1.1 (현재 저장 공식)
   - B: 커미션 × 0.9 (소싱 공식)
   - C: 커미션 전액
5. **프리랜서에게서 부가세 몫을 빼는가.** 사업자등록이 없는 프리랜서에게 부가세를 떼는지 여부.
6. **반올림 단위와 시점.** 원 단위 반올림·절사 여부와, 항목별로 반올림한 뒤 합산하는지 최종액만 반올림하는지.
7. **확정 정산 소급 여부.** 공식을 바꾼 뒤 기존 `pending` 정산을 재계산할지. `confirmed`/`paid`는 재계산하지 않는 것을 권장하며, 이번 작업에서도 건드리지 않았다.

### 결정 후 작업 (별도 승인)

- 하나의 공식 함수로 통일하고, 세 위치가 모두 그 함수를 호출하게 한다.
- 가상 금액 표(위 예시)를 테스트 기대값으로 고정한다.

## D2. 날짜 기준 캠페인 완료 시 정산 자동 생성 여부

### 이번 작업으로 바뀐 점

- `GET /campaigns`는 더 이상 상태·보관·정산을 바꾸지 않는다.
- 일정 기준 처리는 관리자 화면 `/campaigns/progress-review`에서 미리보기 후 선택 적용한다.
  - 대상: 계약완료·진행중 캠페인
  - 기획중·협의중 캠페인은 날짜가 지나도 바꾸지 않는다.
- 이 화면의 "정산 초안 생성" 체크는 **기본 해제**다. 체크하면 정산이 하나도 없는 캠페인에만 `pending` 정산을 만든다.
- 사람이 캠페인을 직접 "완료"로 저장할 때 정산을 만들거나 `pending`을 재계산하는 기존 동작은 유지했다.

### 선택지

| 선택지 | 내용 | 영향 |
|---|---|---|
| A (현재 기본) | 날짜 기준 완료 시 정산 생성 안 함. 사람이 필요할 때 체크 | 정산 누락 가능 → 진행 상태 정리 화면의 "완료인데 정산 없음" 목록으로 확인 |
| B | 체크 기본값을 켬 | 매출이 확정되지 않은 캠페인에도 `pending` 정산이 생길 수 있음 |
| C | 매출 확정 플래그를 따로 두고, 확정된 캠페인만 정산 생성 | 스키마 변경 필요 (컬럼 추가) |

### 추가로 결정할 것

- 진행 상태 정리를 **주기적으로 누가 실행**할지. 자동 스케줄 등록은 하지 않았다.
- 계약완료·진행중 → 완료 전환도 사람이 확인해야 하는지. 현재는 선택 적용 방식이다.

## D3. 외부 쇼핑몰 주문 API (`POST /orders/api/create`)

### 이번 작업으로 바뀐 점 (로컬만, 운영 미반영)

- 토스 서버 조회로 `status=DONE`과 결제액이 서버 계산 금액과 같은지 확인한 경우에만 `paid` 주문을 만든다.
- 같은 `payment_key`로 다시 호출하면 기존 주문을 돌려준다.

### 확인·결정해야 할 것

1. **blend-pick(외부 쇼핑몰)의 실제 호출 여부와 요청 형식.** 이 저장소에는 호출 코드가 없다.
   - 새 필수 항목: `payment_key`, `sales_page_id`, 고객·배송 정보
   - 선택 항목: `option_name`, `quantity`, `addon_items`, `order_id`(토스 orderId)
2. **금액 계산 규칙이 blend-pick과 같은가.** 서버 계산은 옵션가(없으면 판매가) × 수량 + 추가상품 + 판매페이지 배송비다. 다르면 정상 주문이 409로 거부된다.
3. **외부 주문도 매출 거래(Transaction) 생성·재고 차감을 할지.** 내부 쇼핑몰 승인 경로는 하고, 외부 경로는 이전에도 하지 않았고 지금도 하지 않는다.
4. **검증 실패 건 처리.** 결제는 됐는데 금액 불일치로 거부된 건을 누가 어떻게 확인·환불할지. 현재는 로그만 남긴다.

## D4. 기존 데이터 정리 (이번 작업에서 변경하지 않음)

| 항목 | 개발 DB(`blendpunch`) 읽기 조회 결과 | 결정 |
|---|---|---|
| 표준 목록 밖 카테고리 | `유아/육아용품` 24건, `주방용품/식품관련기기` 3건 | 일괄 변환 여부. 코드는 `유아/육아용품`→`유아/육아`를 새 입력에만 매핑하고, 기존 값은 편집 화면에서 보존한다 |
